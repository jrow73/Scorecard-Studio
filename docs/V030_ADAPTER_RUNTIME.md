# Scorecard Studio v0.3.0 — Adapter and Planner Runtime

**Introduced:** Build 004.2  
**Production modules:** `js/v030-adapter-definitions.js` and `js/v030-adapters.js`  
**Contract authority:** `docs/V030_ADAPTER_CAPABILITY_CONTRACTS.md`  
**Machine source:** `tests/fixtures/model-contract/v030-adapter-registry.json`

## 1. Boundary

The adapter runtime defines what may be requested, how request meaning is keyed, whether a source is supported in context, how consumer capabilities become staged work, and how execution outcomes are represented.

It does not contain URLs, perform HTTP, parse raw responses, write caches, normalize final game values, or alter the current app bootstrap. Build 004.2 therefore has no user-visible behavior.

## 2. Production declarations

`v030-adapter-definitions.js` contains a deep-frozen copy of the ten-adapter registry:

- Schedule;
- Feed;
- Boxscore;
- Roster;
- People;
- Coaches;
- Standings;
- Venue;
- Depth Chart; and
- Team Logo.

The declarations are generated by `tools/generate-v030-adapter-definitions.mjs`. The executable test requires exact equality with the machine registry, preventing hand-edited drift.

## 3. Semantic inputs and request keys

`materializeAdapterInput(adapterId, supplied)`:

1. rejects unknown fields;
2. applies declared defaults;
3. requires all mandatory fields;
4. validates strings, integers, booleans, enums, dates, timestamps, and set element types;
5. enforces declared integer minimums; and
6. canonicalizes set-like arrays by deduplication and stable sorting.

The caller's object and arrays are not mutated.

`buildSemanticRequestKey(adapterId, supplied)` produces:

```text
<adapter>|v1|<field>=<encoded-value>|...
```

Fields use declared key order. Every semantic input is keyed, declared defaults are explicit, and array values are canonical before UTF-8 percent encoding. The key identifies request meaning, not a literal URL.

## 4. Capability resolution

`resolveAdapterCapability(adapterId, context)` selects the single most-specific matching rule. Context can include sport ID, game type, competition segment, and requested concept.

Resolution states drive automatic planning:

| State | Planner behavior |
|---|---|
| `supported` | May plan automatically. |
| `conditional` | May plan with the declared limitation/fallback retained. |
| `absent` | Do not request automatically; use the declared fallback. |
| `untested` | Block automatic execution pending evidence or explicit future override. |

Equal-specificity winners raise `CAPABILITY_AMBIGUOUS`. A missing default raises `CAPABILITY_DEFAULT_MISSING`.

## 5. Normalized planner capabilities

The planner accepts exactly:

- `corePregame`;
- `officials`;
- `extendedVenue`;
- `staff`;
- `pitcherRoles`;
- `currentTeamLogos`;
- `game2Overlay`; and
- `standingsGroups`.

`planAdapterRequests({ capabilities, context, requests })` returns decision entries plus deduplicated executable request units. Entry statuses are:

| Status | Meaning |
|---|---|
| `planned` | A complete, supported/conditional semantic request is ready. |
| `pending-input` | The route is known but a staged semantic input is not available yet. |
| `satisfied` | An already-loaded accepted source satisfies the capability. |
| `fallback` | The source is known absent and the declared fallback applies. |
| `suppressed` | Context says the conditional work must not execute. |
| `blocked` | Source/context is untested and automatic execution is prohibited. |

Examples:

- People remains pending until relevant person IDs are discovered.
- Feed venue detail satisfies `extendedVenue` without a Venue request when already usable.
- A core Standings response satisfies `standingsGroups` when it already contains those groups.
- MiLB depth-chart absence selects the roster-minus-starter fallback.
- `game2Overlay` is suppressed until the earlier same-day game is Final.

The planner does not treat a missing staged input as a network failure.

## 6. People chunking and partial failure

`partitionPeopleIds` deduplicates and numerically sorts IDs before fixed-size partitioning. `planPeopleChunks` returns a parent semantic request plus independently keyed chunk units. Chunk boundaries are deterministic for a given canonical ID set and configured chunk size.

`createAdapterUnitResult`, `createAdapterExecutionEnvelope`, and `mergePeopleChunkUnits` preserve these rules:

- successful candidates survive other chunk failures;
- a mixed success/failure operation is `partial`;
- every failed unit retains its error and request key;
- failed people receive `state: failed`; and
- no failed person receives zero statistics.

An execution envelope validates that failure codes belong to the selected adapter. A successful unit cannot also carry an error.

## 7. Integration rules for Build 004.3+

1. Orchestration supplies semantic inputs; it never constructs request keys independently.
2. Network code executes only `planned` units.
3. `pending-input`, `fallback`, `suppressed`, and `blocked` decisions remain visible to diagnostics.
4. Raw parsers emit candidates into adapter envelopes; they do not select final normalized values.
5. Snapshot normalization converts execution envelopes into schema-v2 source results and lineage through the Build 004.1 runtime.
6. Cache identity uses the semantic request key plus adapter contract revision as defined in Build 003.3.
7. The generated declaration module must be regenerated and equality-tested whenever the adapter registry changes.

## 8. Build 004.7 persistence binding

`js/v030-persistence.js` now implements the dormant adapter-cache boundary described above. Adapter-result identity is the adapter contract revision plus the complete semantic request key. Only normalized candidate units are retained; complete raw responses are not persisted.

Partial records retain successful units and expose retryable failed units as the only retry plan. Failed-only executions are skipped, and an adapter declaring `emptyIsFailure` cannot create an empty-success cache entry. Event/scope freshness uses each adapter's declared triggers, while the Team Logo adapter alone applies its evidence-backed numeric TTL.

The persistence controller remains disconnected from application bootstrap until Build 004.8.
